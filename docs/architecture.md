# Архитектура: сбор метрик в момент скрейпа

## Вычисления в момент запроса, а не фоновый цикл

Экспортер собирает метрики Docker в методе `collect()` класса `DockerCollector`, который наследует `Collector` из prometheus_client. Prometheus вызывает `collect()` при каждом `GET /metrics` — обычно раз в 15 секунд.

### Почему именно так

**Проблема фонового цикла:**
- В ранних версиях использовался глобальный объект `Gauge` и цикл `while True: collect(); sleep(15)`.
- Значения хранились в памяти между скрейпами.
- Когда контейнер удалялся, его label-set оставался в метрике навечно. Удаление вручную требовало итерации по `metric.collect()` и вызова `metric.remove()` для каждого исчезнувшего контейнера.
- Значения соответствовали состоянию ~15 секунд назад, а не моменту скрейпа.

**Решение через custom Collector:**
- `DockerCollector` не хранит состояние между скрейпами.
- Каждый вызов `collect()` создаёт свежий снимок (snapshot) всех контейнеров.
- Исчезнувшие контейнеры исключаются автоматически — новый список не содержит их, и их серии просто не эмитятся.
- Значения всегда соответствуют моменту скрейпа.

### Обработка ошибок в collect()

Исключение, выброшенное из `collect()`, превращает ответ `/metrics` в HTTP 500 и убивает даже self-метрики экспортера (build_info, scrape_duration и т.д.). Поэтому:

- Все исключения ловятся: `DockerException` и `requests.RequestException` (недоступен демон) плюс `Exception` (неожиданные ошибки). Оба типа для демона нужны потому, что SDK оборачивает ошибки соединения в `DockerException` не на всех путях: пропавший на лету демон всплывает из `api.containers()` как голый `requests.ConnectionError`.
- При недоступности демона:
  - Счётчик `_scrape_errors` инкрементируется.
  - Метрика `docker_up` возвращается со значением 0 (см. раздел "Self-метрики").
  - Демон был в `_last_reachable=True`? Логируется `ERROR`.
  - Демон снова доступен? Логируется `INFO`.
- Экспортер продолжает отвечать 200 на `/metrics`.

### Многопоточный inspect контейнеров

Метод `_snapshot()` выполняет два этапа:

1. **Список контейнеров** (`/containers/json`): GET один раз в скрейп.
   - Возвращает State, Health, Labels, ImageID, Created для всех контейнеров.

2. **Детали каждого контейнера** (`/containers/{id}/json`): выполняется параллельно.
   - Нужны: RestartCount, ExitCode, StartedAt, OOMKilled.
   - Эти поля есть только в inspect, не в list.
   - Параллелизм через `ThreadPoolExecutor(max_workers=EXPORTER_INSPECT_WORKERS)`, по умолчанию 8.
   - Если контейнер удалили между list и inspect: catch `NotFound`, логируется на DEBUG, скрейп не падает.

**Поля, которые берутся из list:**
```python
State, Health, Labels, ImageID, Created, Names
```

**Поля из inspect:**
```python
RestartCount, ExitCode, StartedAt, OOMKilled, HostConfig.RestartPolicy
```

### Управление сокетом Docker и таймауты

- Клиент создаётся с `timeout=DOCKER_TIMEOUT_SECONDS` (по умолчанию 10 сек), чтобы зависший демон не вешал скрейп.
- Клиент кэшируется в `_client` (переиспользуется между скрейпами).
- При любой ошибке демона вызывается `_drop_client()`: клиент закрывается, следующий скрейп пересоздаст его.
  - Это нужно потому, что если демон рестартует, пул соединений в старом клиенте сломан.

### Graceful shutdown

- Главный поток ждёт `threading.Event` (stop).
- `serve_forever()` крутится в отдельном потоке (server_thread).
- Обработчик SIGTERM/SIGINT выставляет stop.set().
- Главный поток вызывает `httpd.shutdown()` и `httpd.server_close()`.
- Это необходимо потому, что вызов `shutdown()` из того же потока, где крутится `serve_forever()`, приводит к дедлоку.

## Альтернативы, которые были отвергнуты

### 1. Кэш + фоновый цикл с ручной зачисткой

**Идея:** глобальный dict с последними значениями, периодическая зачистка старых серий.

**Проблемы:**
- Сложнее код (состояние между скрейпами, синхронизация).
- Всё равно существует окно времени, когда удалённый контейнер остаётся в метриках.
- Значения не соответствуют моменту запроса.

**Выбор:** отвергнуто. Custom Collector полностью решает проблему.

### 2. Сбор docker stats для CPU/памяти

**Идея:** добавить метрики использования ресурсов напрямую.

**Проблемы:**
- Каждый вызов `docker stats` блокирует ~1-2 секунды на контейнер (даже при параллелизме это замедлит скрейп).
- Это дублирует cAdvisor — отдельный экспортер от Google, который читает метрики ресурсов напрямую из cgroups и делает это эффективнее.
- Лишние привилегии в API proxy.

**Выбор:** отвергнуто. Пользователь может использовать cAdvisor параллельно для CPU/памяти.

### 3. Последовательный inspect (без параллелизма)

**Идея:** вызывать inspect для каждого контейнера по очереди.

**Проблемы:**
- Сам по себе inspect дешёвый — единицы миллисекунд через unix-сокет. Но это один round-trip на контейнер, и на хосте с сотнями контейнеров задержки складываются в заметную долю скрейпа.
- Скрейп-бюджет ограничен: `scrape_timeout` в Prometheus стоит 12 с, а клиент Docker — 10 с.

**Выбор:** отвергнуто, но разница не драматическая. ThreadPoolExecutor убирает суммирование round-trip'ов; ускорение упирается в демон и в GIL на разборе JSON, поэтому 8 воркеров не означают ровно 8x. Число настраивается через `EXPORTER_INSPECT_WORKERS`.

## Общая диаграмма потока

```
GET /metrics
    ↓
Prometheus вызывает collector.collect()
    ↓
_snapshot():
    ├─ _list_containers()  [одни раз, 1x HTTP GET]
    └─ ThreadPoolExecutor.map(_inspect)  [параллельно, 8 потоков]
        └─ Каждый inspect() -> (container_id, details dict)
            └─ Catch NotFound, логирование на DEBUG
    ↓
_normalise(raw, detail) -> dict с полями для метрик
    ↓
collect() эмитит:
    ├─ docker_up = 1/0 (демон доступен?)
    ├─ docker_exporter_build_info
    ├─ docker_daemon_info (если snapshot != None)
    ├─ docker_exporter_containers_scraped
    ├─ docker_exporter_scrape_duration_seconds
    ├─ docker_exporter_scrape_errors_total
    └─ Метрики контейнеров (state, health, restarts и т.д.)
    ↓
HTTP 200, body = текст метрик Prometheus
```
